# Design decisions

A short log of the choices behind the classifier: what we chose, the number that motivated it, and
the course reference. Newest entries at the bottom. Every number comes from a file in `results/`
or from the exploration notebook.

| Date | Decision | Evidence | Reference |
|---|---|---|---|
| 2026-10-17 | Data: `coastalcph/lex_glue`, config `ledgar`, pinned to Hub commit `c23fdff1` (2024-01-04). The three official splits are used as they are (train 60 000 / validation 10 000 / test 10 000): no re-split, no shuffle. | The validation split already exists; re-splitting would make our numbers incomparable with LexGLUE. | S01 p12 ("every decision taken on the test set makes the test score optimistic") |
| 2026-10-17 | Decision metric: **macro-F1** on validation; accuracy (= micro-F1) reported next to it. | 100 classes, very imbalanced (largest / smallest class ≈ 138× on train). | S01 p14, S04 p22, TP01 Ex 11 |
| 2026-10-17 | The test split is read once per final model, by the last "predict & save" cell of each training notebook and by the evaluation notebook; every choice (hyperparameters, epoch, `MAX_LENGTH`, LoRA config, class weights) is made on validation. | — | S01 p12, S06 p22 |
| 2026-10-17 | English encoder (`distilbert-base-uncased` as main model, one `bert-base-uncased` reference run); CamemBERT is not used. | LEDGAR clauses come from SEC filings, in English; CamemBERT is pre-trained on French. | TP03 "What we see", S05 p22 |
| 2026-10-17 | Environment pinned to the course versions (torch 2.14.1, transformers 5.19.0, datasets 5.1.0, peft 0.21.2, scikit-learn 1.9.1). The same `requirements.txt` resolves on the Mac (Python 3.14) and on Linux / Python 3.12 (Colab with CUDA, CI with CPU torch). | `uv pip compile` for both platforms. | — |
| 2026-10-17 | Macro-F1 is the mean of per-type F1 over the types that have at least one true clause in the evaluated split (`ledgar.metrics`). | *Books* has 0 validation clauses (23 train, 2 test): validation macro-F1 is always a mean over the same 99 types, whatever a model predicts. On the test split the 100 types are present and the score equals scikit-learn's `f1_score(average="macro")`. | S01 p14 |
| 2026-10-17 | `max_length = 512` for DistilBERT, with `TrainingArguments(train_sampling_strategy="group_by_length")`. Fallback if a T4 runs out of memory: batch 16 with `gradient_accumulation_steps=2`. | Training clauses kept whole: 58.9 % at 128, 86.5 % at 256, 95.1 % at 384, 98.2 % at 512. Tokens per epoch relative to 256 with random batches: 1.77 at 512 with random batches, 0.565 at 512 with length-grouped batches (0.497 at 256 grouped). `reports/data_summary.json`. Decided by the team on these numbers. | TP06 Ex 4, S06 p10, S05 p9 |
| 2026-10-17 | `max_words = 476` for the LSTM. | p99 of training clause length in words (median 86). Packing means the LSTM never pays for padding. | S04 p6, p10 |
| 2026-10-17 | The official test split is kept as it is, although 282 test clauses (2.8 %) are exact copies of a training clause; the final evaluation reports scores separately on clauses seen / not seen in training (`data.seen_in_train`). | Copies are contract boilerplate, not a broken split; 6 texts carry two labels, always close types (Waivers / No Waivers, Severability / Enforceability, Applicable / Governing Laws). | S01 p12 |
| 2026-10-17 | Per-band analysis by training count: tail < 300 clauses (22 types), middle, head ≥ 1 000 (16 types). Types with fewer than 10 test clauses (Books, Assigns, Qualifications) are always shown with their support. | Train counts: quartiles 312 / 427 / 667; only 3 types below 100, too few for a band of their own. | S04 p27 |
| 2026-10-17 | Lazy floor (always *Governing Laws*) saved as the run `results/lazy`, first row of the results table. | Validation: accuracy 0.049, macro-F1 0.001. | TP01 Ex 11 |
| 2026-10-17 | `FAST_RUN=1`: per-class subset (≤ 30 training, ≤ 5 evaluation clauses per type), 1 epoch, `max_length` 128, 200 bootstrap resamples, outputs in `.fast/` (not versioned). | A uniform sample of 2 000 clauses would lose most rare types and break per-class F1. | TP04, TP06 |
| 2026-10-17 | The package never reads the test split; a notebook reads it only in its final "predict & save" cell. Enforced by `tests/test_hygiene.py`. The exploration notebook also reads test **labels** for the class counts per split and the exact-duplicate check, never the lengths or the vocabulary. | — | S01 p12, S04 p5 |
| 2026-10-17 | m1 baseline: TF-IDF on unigrams + bigrams (`min_df` 2, sublinear tf, 173 477 features) and multinomial logistic regression with C = 30, no class weight, solver lbfgs. | Validation macro-F1: 0.827 (C = 30) against 0.819 (C = 10), 0.774 (C = 1, the starting point) and 0.792 for the best unigram model; `class_weight="balanced"` 0.826, so dropped. `results/tfidf/grid_val.csv`. | S01 p21 |
| 2026-10-17 | The m1 grid is not extended beyond C = 30, although the best C is on its edge. | The test predictions of this configuration were already written when we noticed; a configuration chosen after the test is read makes the test score optimistic. Stated as a limit of the baseline. | S01 p12 |
| 2026-10-17 | Solver lbfgs, one fit at a time. | saga is 6× faster on bigrams without weights but did not converge with balanced weights (393 s, ConvergenceWarning); an lbfgs fit on bigrams holds about 3 GB, and two in parallel already swap on the team's 16 GB laptop. | — |
| 2026-10-17 | LSTM batches grouped by length (shuffled mega-batches of 50 batches, sorted inside), as for DistilBERT. | One epoch on the Mac (MPS): 6.4 min with random batches, 1.7 min grouped (BiLSTM: 8.6 → 3.2 min); padding falls to 3.8 % of the positions. | S04 p6 |
| 2026-10-17 | Evaluation and prediction of the Trainer read the dataset in order (`OrderedEvalTrainer`), and `predict_logits` checks it. | With `train_sampling_strategy="group_by_length"`, transformers 5.19 also sorts evaluation batches: the Trainer's own metrics stayed right, but saved predictions no longer lined up with the clauses (val accuracy 0.37 inside the Trainer, 0.01 on our saved predictions in a FAST_RUN check). | — |
| 2026-10-17 | LoRA runs use `peft` (`task_type="SEQ_CLS"`); the hand-written `LoRALinear` / `inject_lora` are kept for the notebook and checked against it. | Same trainable parameters: 147 456 adapter weights + the whole head (`pre_classifier` and `classifier`), 741 124 for 4 classes as in TP06. `peft` also saves the adapter (a few MB, versioned). | S06 p18-20, TP06 Ex 16, 23 |
| 2026-10-17 | The main comparison (full fine-tuning vs LoRA r = 8 on q/v) is written in the README before any m4 run. | — | S06 p26 |
| 2026-10-17 | m4 runs on Colab keep Colab's own `torch` (its CUDA build matches the GPU driver) and pin everything else (`colab/run_m4.ipynb`); each run records the versions it used in `manifest.json`. | Reinstalling torch 2.14.1 on Colab downloads its CUDA 13 libraries (several GB) and may not match the runtime's driver. | — |
| 2026-10-17 | m4 learning rates are searched with validation-only runs that save their weights on Drive; `scripts/predict_test.py` then predicts the test split once for the chosen run, after checking that the saved weights give back its validation predictions. | No GPU time spent retraining the chosen configuration, and no test prediction exists for a configuration that was not chosen. FAST_RUN check: validation reproduced at 100 %. | S01 p12 |
| 2026-10-17 | m3 configuration, chosen one factor at a time on validation macro-F1 (seed 0, 8 epochs): GloVe 50-d initialisation, bidirectional, H = 256, class weights ∝ 1/√count clipped to [0.5, 5]; lr 2e-3 and dropout 0.3 kept. | `results/search/lstm_search.csv`: 0.7452 (TP04 start) → GloVe 0.7454 (same score with half the parameters) → BiLSTM 0.7724 → H 256 0.7753 → lr 1e-3 0.7504 (rejected) → √ weights 0.7764 → dropout 0.5 0.7487 (rejected). Gains under 0.5 point are within the noise of one seed; the three final seeds measure it. GloVe covers 89 % of the vocabulary. | S02 p22, S04 p15, TP04 E, TP05 |
| 2026-10-17 | m3 final runs: 15 epochs instead of 8, the best epoch on validation kept; seeds 0, 1, 2. | Every 8-epoch run of the search had its best validation epoch at the last one. With a constant learning rate and the best epoch kept, a 15-epoch run contains the 8-epoch one, so it cannot do worse on validation; the curves of the final runs show where the best epoch falls. | S01 p12 |
| 2026-10-17 | LSTM runs are sequential on the Mac GPU (MPS). | Two trainings at once are each 3× slower (0.46 s per batch instead of 0.16). | — |
| 2026-10-17 | m3 result: the BiLSTM stays below the TF-IDF baseline; it is kept as the m3 model, not as a production candidate. | Validation macro-F1 0.7895 ± 0.0044 over seeds 0-2 (best epochs 15, 15, 12) against 0.8265 for TF-IDF; behind in every frequency band (tail 0.639 vs 0.673). `notebooks/03_lstm_classifier.ipynb`. | — |
| 2026-10-18 | The Colab runner (`colab/run_m4.ipynb`) chooses each method's learning rate itself, as the one with the best validation macro-F1 among its three search runs, saves the choice to `choice.json` on Drive, and only then predicts the test split and trains the other seeds and variants. Finished runs are skipped, so "Run all" can be repeated after a cut session. | The rule is the one written before the runs; making it automatic lets one person run every m4 run without editing a cell, and no test score is read to make a choice. | S01 p12 |
