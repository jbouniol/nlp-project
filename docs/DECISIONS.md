# Design decisions

A short log of the choices behind the classifier: what we chose, the number that motivated it, and
the course reference. Newest entries at the bottom. Every number comes from a file in `results/`
or from the exploration notebook.

| 2026-10-17 | LSTM runs are sequential on the Mac GPU (MPS). | Two trainings at once are each 3× slower (0.46 s per batch instead of 0.16). | — |

| 2026-10-18 | The Colab runner (`colab/run_m4.ipynb`) chooses each method's learning rate itself, as the one with the best validation macro-F1 among its three search runs, saves the choice to `choice.json` on Drive, and only then predicts the test split and trains the other seeds and variants. Finished runs are skipped, so "Run all" can be repeated after a cut session. | The rule is the one written before the runs; making it automatic lets one person run every m4 run without editing a cell, and no test score is read to make a choice. | S01 p12 |
| 2026-10-18 | Precision and batch sizes follow the device (`config.device_profile`) unless given explicitly: bf16 with TF32 on GPUs with native bf16 (A100, L4, H100), fp16 on the others (T4, V100), fp32 on MPS and CPU. Training batch x accumulation = 32 everywhere: 32 x 1 on a GPU of 14 GB or more, 16 x 2 below (the T4 fallback above, now automatic), 8 x 4 on MPS; the CPU keeps the previous 32 x 1. Evaluation batch: 256 from 40 GB, 64 on smaller GPUs and on CPU, 32 on MPS. A reloaded classifier (`predict.load_classifier`) runs under the precision of its run on CUDA. | The m4 learning rates are searched at an effective batch of 32; keeping it fixed keeps the runs comparable whatever the GPU. bf16 has the exponent range of fp32 (no loss scaling) and is native from Ampere on; a T4 has no bf16 units. The Trainer evaluates under autocast too, so a classifier reloaded in fp32 would not reproduce the saved validation predictions as closely (the 99.9 % gate of `scripts/predict_test.py`). The CPU only runs the FAST_RUN smoke test: with 8 x 4 its LoRA run reloaded with merged adapters reproduced 494 of 495 validation predictions (0.998, CI of PR #1), below the 0.999 gate, so the CPU keeps the values that pass it. The memory thresholds are not measured. | — |

| 2026-10-18 | Follow-up experiment, decided on validation after the 3-epoch runs: the two chosen configurations trained for 10 epochs (`colab/run_m4_10epochs.ipynb`). A method keeps 10 epochs only if its seed-0 validation macro-F1 beats the 3-epoch one; only then are its test split predicted and seeds 1-2 trained. The pre-registered comparison stays the 3-epoch one, reported as registered; the follow-up is reported separately, and the 3-epoch test scores had already been read when it was decided. | Every 3-epoch run was still improving at its last epoch (validation macro-F1 0.705 → 0.762 → 0.791 and validation loss 0.65 → 0.53 → 0.50 for full fine-tuning); the gap with TF-IDF on validation is concentrated in the 22 rare types (mean F1 0.587 against 0.673) while the frequent types are level (0.923 against 0.924). | 2026-10-19 | m2 retrieval protocol: bank = the 60 000 training clauses, queries = the 10 000 validation clauses, test read once for the chosen configuration. Relevance proxy = same clause type as the query. | The only label available; it measures the type, not the wording inside a type, so two within-type checks are added (perturbation self-retrieval, constrained queries). | S01 p12 |
| 2026-10-19 | Encoders compared: TF-IDF cosine, `all-MiniLM-L6-v2`, `e5-small-v2`, `bge-small-en-v1.5`, `distilbert-base-uncased` and `legal-bert-base-uncased` mean-pooled, the m4 LoRA classifier's penultimate features; each dense encoder also centered on the bank mean. No MLM pre-training of ours, no contrastive fine-tuning, no cross-encoder reranker. | Raw BERT embeddings are anisotropic (Ethayarajh 2019) and below GloVe on similarity (Reimers & Gurevych 2019): DistilBERT is the negative control, Legal-BERT the domain-MLM point without GPU hours. A classifier trained with cross-entropy collapses each type on its mean (Papyan et al. 2020): it should win the proxy and lose within-type similarity. Contrastive fine-tuning on same-type pairs would optimise the proxy; a reranker costs 50 passes per query and a second model to audit. | — |
| 2026-10-19 | Perturbation self-retrieval uses validation clauses without a copy in the bank as sources (first half, second half, one sentence removed), ranked among bank + source. | Sources from the bank would give the hybrid filter in-sample classifier probabilities and let the hard filter pass the gate artificially. | S01 p12 |
| 2026-10-19 | Hybrid type filter: hard (argmax type) and soft (`cos + lambda log p(type)`, lambda in 0.1, 0.3, 1, 3), probabilities from the m4 LoRA run `lora_lr1e-3_ep10_seed0` (10 epochs, seed 0) for every decisional run; a TF-IDF refit only under FAST_RUN. `--choose` refuses runs with mixed probability sources. | The production candidate of part 1 is full fine-tuning (10 epochs), but its weights live on Drive only; the LoRA adapter is versioned, so anyone who clones the repository reproduces the hybrid (validation macro-F1 0.807 against 0.820, 1.3 points below). Mixing sources would make the hybrid grid incomparable across encoders. | — |
| 2026-10-19 | Pre-registered rule, written before any retrieval run: candidates = encoder x {raw, centered} x {dense, soft lambda, hard}; gate = perturbation MRR >= 0.95 x the best perturbation MRR over all candidates; choice = best validation macro P@10 among gated candidates; ties to fewer components. Two final models on test: the chosen variant and the dense variant of the same encoder. | Without the gate, the classifier features and the hard filter win the proxy by construction while losing the wording inside a type, the lawyer's actual use. The gate is relative, so it applies to every candidate the same way. | S01 p12, S06 p26 |
