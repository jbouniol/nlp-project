# LEDGAR clause classifier

The classification part of a contract-review assistant: given one clause of a contract, predict its
type among the 100 clause types of [LEDGAR](https://huggingface.co/datasets/coastalcph/lex_glue)
(LexGLUE). Four models, from a cheap baseline to a fine-tuned transformer, evaluated with macro-F1
on the official held-out test set and compared with paired tests.

| Milestone | Model | Notebook |
|---|---|---|
| m1 | TF-IDF + logistic regression | `notebooks/01_explore_ledgar.ipynb`, `notebooks/02_baseline_tfidf.ipynb` |
| m3 | BiLSTM + GloVe | `notebooks/03_lstm_classifier.ipynb` |
| m4 | DistilBERT, full fine-tuning and LoRA | `notebooks/04_finetune_distilbert.ipynb`, `notebooks/05_lora.ipynb`, `notebooks/06_evaluation.ipynb` (GPU runs: `colab/`) |

## Results

- **On the 10 000 test clauses, the best model is DistilBERT fully fine-tuned for 10 epochs: macro-F1
  0.827 ± 0.004** over three seeds. It is **not significantly better than the TF-IDF baseline (0.829)**: macro-F1
  difference −0.003, 95 % paired-bootstrap interval [−0.013, +0.007], McNemar p = 0.60. A transformer is not worth
  its cost on this dataset unless the contracts it will meet differ from LEDGAR's.
- **Registered comparison** (3 epochs, written below before any m4 run): full fine-tuning and LoRA have the same
  macro-F1, but full fine-tuning is right more often (McNemar p = 0.002), so the rule names full fine-tuning.
- After 10 epochs, full fine-tuning leads LoRA by 1.1 points of macro-F1 (significant); LoRA trains 1.2 % of the
  parameters and needs four times less memory to train.
- Every model fails mostly on near-synonym types (*Applicable* / *Governing Laws*, *Tax Withholdings* /
  *Withholdings*) and on the rare types; see the [model card](reports/model_card.md) for what the model must not
  be used for.

## Pre-registered comparison

*Written and committed before any m4 model was trained (S06 p26: "the main comparison written in the README
before running it, then its paired test").*

**Question.** Full fine-tuning of DistilBERT trains 67 M parameters; LoRA trains 0.7 M (rank-8 adapters on the
query and value projections, plus the new head). Is the full model worth it?

**Hypothesis.** On the LEDGAR test set (10 000 clauses, seed 0), full fine-tuning of `distilbert-base-uncased`
has a higher macro-F1 than LoRA (r = 8, α = 16, `q_lin` and `v_lin`), by at most 1 point, and the difference
is not significant.

**Setting.** Same data, `max_length` 512 with length-grouped batches, 3 epochs, warmup 10 % then linear decay,
the epoch with the best validation macro-F1 kept; each method's learning rate chosen on validation
(full: 2e-5, 3e-5, 5e-5; LoRA: 3e-4, 5e-4, 1e-3). The test set is predicted once per model.

**Tests.** McNemar's test on the per-clause correctness (continuity correction; exact binomial test if
b + c < 25), and a paired bootstrap of the macro-F1 difference (1 000 resamples, seed 0, 95 % percentile
interval), at α = 5 %.

**Decision rule.** If the bootstrap interval contains 0 and McNemar's p ≥ 0.05, LoRA is the production
candidate; otherwise full fine-tuning is.

Secondary comparisons, same tests: the best transformer vs the TF-IDF baseline (is a transformer worth its
cost?), the transformer vs the LSTM, and LoRA on every linear layer vs LoRA on `q_lin`, `v_lin`.

## Outcome of the registered comparison

*Tested in `notebooks/06_evaluation.ipynb`, seed 0 of each model, as written above.*

| | full fine-tuning | LoRA | difference (95 % interval) | McNemar |
|---|---|---|---|---|
| registered, 3 epochs | 0.7781 | 0.7826 | −0.0045 [−0.0147, +0.0098] | b = 323, c = 249, p = 0.002 |
| follow-up, 10 epochs | 0.8259 | 0.8144 | +0.0114 [+0.0020, +0.0200] | b = 356, c = 306, p = 0.057 |

**Registered verdict: full fine-tuning.** The macro-F1 difference is within a point and not significant, as
hypothesised, but McNemar's test finds full fine-tuning right more often, so the rule does not choose LoRA. The
hypothesis is half confirmed.

**Follow-up.** Every 3-epoch run was still improving at its last epoch, so both configurations were trained for 10
epochs (decided on validation, after the registered runs; reported separately). Full fine-tuning then leads by a
significant 1.1 points: it is the production candidate, and LoRA the lighter alternative.

## Design decisions

One line per choice; the figures behind each one are in [`docs/DECISIONS.md`](docs/DECISIONS.md).

- Official LexGLUE splits, unchanged, dataset revision pinned; the test split is read once per final model.
- Macro-F1 as the decision metric, averaged over the types present in the evaluated split (*Books* has no
  validation clause).
- TF-IDF: unigrams and bigrams, logistic regression with C = 30, no class weights (grid on validation).
- BiLSTM: chosen one factor at a time on validation; reading in both directions is the only change worth more than
  half a point.
- DistilBERT (English) rather than CamemBERT (French): LEDGAR clauses are English SEC filings. 512 tokens with
  length-grouped batches keep 98.2 % of clauses whole for less compute than 256 tokens with random batches.
- Learning rates chosen on validation (5e-5 full, 1e-3 LoRA); 10 epochs kept because validation improved.
- Paired tests (McNemar and bootstrap) for every comparison, never two scores side by side.

## How to reproduce

```bash
make setup      # .venv with the pinned course environment, package installed in editable mode
make test       # unit tests
make smoke      # the whole pipeline on a per-class subset (FAST_RUN=1), then every notebook
```

GPU runs (m4) on Colab: open [`colab/run_m4.ipynb`](https://colab.research.google.com/github/jbouniol/nlp-project/blob/main/colab/run_m4.ipynb),
the run cards of every DistilBERT and LoRA run, in order.
The 10-epoch follow-up has its own runner,
[`colab/run_m4_10epochs.ipynb`](https://colab.research.google.com/github/jbouniol/nlp-project/blob/main/colab/run_m4_10epochs.ipynb). From the command line:

```bash
python scripts/train.py --model tfidf                                  # m1 (= make m1)
python scripts/search_lstm.py                                          # m3: one factor at a time, on validation
python scripts/train.py --model lora --search --lr-lora 1e-3 --seed 0  # m4: a validation-only run
python scripts/predict_test.py --name lora_lr1e-3_seed0                # the chosen run predicts the test split, once
```
