# LEDGAR clause classifier

The classification part of a contract-review assistant: given one clause of a contract, predict its
type among the 100 clause types of [LEDGAR](https://huggingface.co/datasets/coastalcph/lex_glue)
(LexGLUE). Four models, from a cheap baseline to a fine-tuned transformer, evaluated with macro-F1
on the official held-out test set and compared with paired tests.

| Milestone | Model | Notebook |
|---|---|---|
| m1 | TF-IDF + logistic regression | `notebooks/01_explore_ledgar.ipynb`, `notebooks/02_baseline_tfidf.ipynb` |
| m3 | BiLSTM + GloVe | `notebooks/03_lstm_classifier.ipynb` |
| m4 | DistilBERT, full fine-tuning and LoRA | `notebooks/04_finetune_distilbert.ipynb`, `notebooks/05_lora.ipynb`, `notebooks/06_evaluation.ipynb` (GPU runs: `colab/`) |
| m2 | clause retrieval: sentence-transformer index, hybrid type filter | `notebooks/07_retrieval.ipynb` |

## Results

- **On the 10 000 test clauses, the best model is DistilBERT fully fine-tuned for 10 epochs: macro-F1
  0.827 ± 0.004** over three seeds. It is **not significantly better than the TF-IDF baseline (0.829)** on seed 0
  (macro-F1 difference −0.003, 95 % paired-bootstrap CI [−0.013, +0.007], McNemar p = 0.60) or across all 3 seeds
  (3-seed mean difference −0.002, 95 % CI [−0.010, +0.006]). A transformer is not worth its cost on this dataset
  unless the contracts it will meet differ from LEDGAR's.
- **Registered comparison** (3 epochs, written below before any m4 run): full fine-tuning and LoRA have the same
  macro-F1 (3-seed mean difference +0.002, 95 % CI [−0.005, +0.013]), but full fine-tuning is right more often on
  every seed (McNemar p = 0.0023, < 0.0001, 0.0006), so the rule names full fine-tuning.
- After 10 epochs, full fine-tuning leads LoRA by +1.14 points on seed 0 (95 % CI [+0.002, +0.020]) and +1.26 points
  across all 3 seeds (95 % CI [+0.0054, +0.0193]); LoRA trains 1.2 % of the parameters and needs four times less
  memory to train.
- **Confidence calibration & bias audit:** training for 10 epochs inflates test ECE from 0.033 to **0.086** (57.1 %
  of test errors have confidence > 0.90); post-hoc temperature scaling fitted on validation ($T = 2.47$) cuts test ECE
  by 73 % to **0.023** (and by 84 % to **0.011** on LoRA 10 ep with $T = 2.23$). Every model fails mostly on
  near-synonym types (*Applicable* / *Governing Laws*, *Tax Withholdings* / *Withholdings*) and on the rare types;
  across inferred contract families and party roles (`reports/bias_audit.md`, `reports/figures/bias_audit_slices.png`),
  accuracy drops from 89–91 % on credit/loan, M&A and securities clauses to **75.8 % on leases & licenses** (macro-F1
  **0.657 [0.600, 0.727]**, retrieval P@10 **0.576**) and **73.4 % on landlord / tenant / licensor clauses** (macro-F1
  **0.634 [0.573, 0.712]**), while ALL-CAPS boilerplate drops to **0.517 [0.454, 0.667] macro-F1** across the 29 types
  that appear in uppercase. See the [model card](reports/model_card.md) for what the model must not be used for.

## Pre-registered comparison

*Written and committed before any m4 model was trained (S06 p26: "the main comparison written in the README
before running it, then its paired test").*

**Question.** Full fine-tuning of DistilBERT trains 67 M parameters; LoRA trains 0.7 M (rank-8 adapters on the
query and value projections, plus the new head). Is the full model worth it?

**Hypothesis.** On the LEDGAR test set (10 000 clauses, seed 0), full fine-tuning of `distilbert-base-uncased`
has a higher macro-F1 than LoRA (r = 8, α = 16, `q_lin` and `v_lin`), by at most 1 point, and the difference
is not significant.

**Setting.** Same data, `max_length` 512 with length-grouped batches, 3 epochs, warmup 10 % then linear decay,
the epoch with the best validation macro-F1 kept; each method's learning rate chosen on validation
(full: 2e-5, 3e-5, 5e-5; LoRA: 3e-4, 5e-4, 1e-3). The test set is predicted once per model.

**Tests.** McNemar's test on the per-clause correctness (continuity correction; exact binomial test if
b + c < 25), and a paired bootstrap of the macro-F1 difference (1 000 resamples, seed 0, 95 % percentile
interval), at α = 5 %.

**Decision rule.** If the bootstrap interval contains 0 and McNemar's p ≥ 0.05, LoRA is the production
candidate; otherwise full fine-tuning is.

Secondary comparisons, same tests: the best transformer vs the TF-IDF baseline (is a transformer worth its
cost?), the transformer vs the LSTM, and LoRA on every linear layer vs LoRA on `q_lin`, `v_lin`.

## Outcome of the registered comparison

*Tested in `notebooks/06_evaluation.ipynb`, on seed 0 (as pre-registered) and across all 3 seeds (`stats.compare_seeds`).*

| | full fine-tuning | LoRA | seed-0 difference (95 % CI) | 3-seed mean difference (95 % CI) | McNemar (seed 0; seeds 0–2 p) |
|---|---|---|---|---|---|
| registered, 3 epochs | 0.7781 (3-seed: 0.7836) | 0.7826 (3-seed: 0.7816) | −0.0045 [−0.0147, +0.0098] | +0.0019 [−0.0054, +0.0130] | b = 323, c = 249, p = 0.0023 (0.0023, <1e-4, 0.0006) |
| follow-up, 10 epochs | 0.8259 (3-seed: 0.8270) | 0.8144 (3-seed: 0.8144) | +0.0114 [+0.0020, +0.0200] | +0.0126 [+0.0054, +0.0193] | b = 356, c = 306, p = 0.0569 (0.0569, 0.0043, 0.39) |

**Registered verdict: full fine-tuning.** The macro-F1 difference is within a point and not significant, as
hypothesised, but McNemar's test finds full fine-tuning right more often, so the rule does not choose LoRA. The
hypothesis is half confirmed.

**Follow-up.** Every 3-epoch run was still improving at its last epoch, so both configurations were trained for 10
epochs (decided on validation, after the registered runs; reported separately). Full fine-tuning then leads by a
significant 1.1 points: it is the production candidate, and LoRA the lighter alternative.

## Design decisions

One line per choice; the figures behind each one are in [`docs/DECISIONS.md`](docs/DECISIONS.md).

- Official LexGLUE splits, unchanged, dataset revision pinned; the test split is read once per final model.
- Macro-F1 as the decision metric, averaged over the types present in the evaluated split (*Books* has no
  validation clause).
- TF-IDF: unigrams and bigrams, logistic regression with C = 30, no class weights (grid on validation).
- BiLSTM: chosen one factor at a time on validation; reading in both directions is the only change worth more than
  half a point.
- DistilBERT (English) rather than CamemBERT (French): LEDGAR clauses are English SEC filings. 512 tokens with
  length-grouped batches keep 98.2 % of clauses whole for less compute than 256 tokens with random batches.
- Learning rates chosen on validation (5e-5 full, 1e-3 LoRA); 10 epochs kept because validation improved.
- Paired tests (McNemar and bootstrap) for every comparison, never two scores side by side.

## Part 2: clause retrieval (m2)

Given a pasted clause or a lawyer's question, return the most similar clauses of a clause bank. Bank = the 60 000
training clauses; queries = the 10 000 validation clauses; the test split is read once at the end, for the chosen
configuration. A retrieved clause counts as relevant when it has the clause type of the query: a proxy that
measures the type, not the wording inside a type, so it is completed by two within-type checks.

**Encoders compared on validation.** TF-IDF cosine (the lexical baseline), three off-the-shelf sentence
transformers (`all-MiniLM-L6-v2`, `e5-small-v2`, `bge-small-en-v1.5`), `distilbert-base-uncased` mean-pooled (a
negative control: raw encoders are anisotropic), `legal-bert-base-uncased` mean-pooled (a domain MLM, no training
of ours) and the penultimate features of the m4 LoRA classifier (expected to win the type proxy and lose the
wording inside a type). Every dense encoder is also evaluated after centering on the bank mean. Exact search by
matrix product; no index approximation.

**Evaluations.** (1) clause -> clause: P@1, P@5, P@10 and MRR, macro-averaged over clause types, by frequency band,
seen / not seen in training, truncated / whole; the 10-nearest-neighbour vote is also scored as a classifier
(macro-F1). (2) The 100 type names as zero-shot queries. (3) Self-retrieval under perturbation: 1 000 validation
clauses without a copy in the bank, each cut to its first half, its second half, or with one sentence removed, must
retrieve themselves at rank 1 among the bank (Hit@1, MRR): the within-type check. (4) About 15 lawyer questions with
a regex-checkable constraint ("termination clauses with a 30-day notice period"): type precision, constraint
precision among the retrieved clauses of the type, and the lift over the base rate of the constraint in that type.
(5) Geometry of the bank embeddings: anisotropy, effective rank, hubness, alignment / uniformity.

**Hybrid.** The classifier of part 1 predicts the type of the query; the bank is then restricted to that type
(hard) or re-scored with `cos + lambda * log p(type)` (soft, lambda in {0.1, 0.3, 1, 3}). The probabilities come
from the m4 LoRA run `lora_lr1e-3_ep10_seed0` for every decisional run (adapter versioned in `results/`; the full fine-tuning
weights of the production candidate live on Drive only).

**Pre-registered decision rule** (written before any retrieval run). Candidates = every encoder x {raw, centered} x
{dense, soft lambda, hard}. Gate: perturbation MRR >= 0.95 x the best perturbation MRR over all candidates. Choice =
the best macro P@10 on validation among the gated candidates; ties go to the variant with fewer components (dense
before soft before hard, raw before centered). The chosen variant and the dense variant of the same encoder are the
two final models evaluated on the test split, once, with a paired bootstrap of their macro P@10 difference. The
natural-language query results are reported, not decisional.

**Out of scope, with their cost.** Our own MLM pre-training (GPU hours for an objective that does not teach
similarity; Legal-BERT stands in), contrastive fine-tuning on same-type pairs (optimises the proxy we know is
partial), a cross-encoder reranker (50 forward passes per query, a second model to audit).

**Outcome of the pre-registered rule and semantic-separated selection** (`results/retrieval/choice.json`).
- **All-pooled lexical rule (`retrieval.choose`):** 78 candidates (13 encodings x {dense, soft lambda in 0.1, 0.3, 1, 3,
  hard}); gate = 0.95 x the best perturbation MRR (0.897, TF-IDF) = 0.852; **one candidate passed: TF-IDF cosine,
  dense** (because a half-clause shares 100 % of its words with its source clause). On the 10 000 test clauses, read
  once: macro P@10 **0.658** (validation 0.661), MRR 0.873, 10-NN vote macro-F1 0.737; head types 0.83, middle 0.70,
  tail 0.43.
- **Semantic-separated selection (`retrieval.choose_semantic` and `retrieval.choose_nl`):** separating the lexical
  baseline from dense encoders (within-type gate $\text{MRR} \ge 0.95 \times 0.761 = 0.723$ and zero-shot NL floor
  $\text{P@10} \ge 0.50$) keeps 4 dense candidates (`bge+center`, `bge`, `e5`, `e5+center`) and selects **`bge+center`
  (`dense`)** for clause-to-clause similarity (**0.669** validation macro P@10, significantly beating TF-IDF's 0.661
  by **+0.76 pts**, 95 % CI [+0.27, +1.21], and by **+1.85 pts macro / +4.64 pts micro** on the low-lexical-overlap
  quartile $n = 2\,502$) and **`e5` (`dense`)** for natural-language lawyer questions (**86.2 %** constraint precision,
  4.0× lift, **0.591** type-name P@10).

What the runs showed, in the order of the notebook:

- The type proxy does not separate the encoders (macro P@10 0.61-0.67; the classifier's own features 0.758). The
  within-type check does: a clause cut in half finds its source with MRR 0.90 under TF-IDF, 0.63-0.76 under every
  dense encoder, 0.51 under the classifier's features, whose per-type collapse is the one predicted above.
- Every hybrid variant of every encoder scores 0.80-0.81: that is the LoRA classifier's type accuracy, not
  retrieval, and it costs 8 to 28 points of within-type MRR against the encoder's own dense variant (a wrong
  predicted type removes the source clause).
  The type is worth a filter the lawyer ticks, not one the classifier guesses.
- Raw MLM encoders live in a cone (mean cosine between random clauses 0.80-0.88); centring recovers about a point.
  TF-IDF's weakness is hubness: one boilerplate "entire agreement" clause appears in 414 of the 60 000 top-10 lists.
- For lawyer *questions* the order reverses, and it is reported, not decisional: contrastive sentence encoders
  answer type names (P@10 0.53-0.59) and keep the asked constraint in 76-88 % of the retrieved clauses of the right
  type (e5 and MiniLM 86-88 %, lift 4 over the base rate; means over the questions where that type was retrieved),
  TF-IDF 0.48 and 75 %, Legal-BERT and DistilBERT 0.02-0.05 and no better than the base rate. A dense entry point for
  questions, with TF-IDF for pasted clauses, would need its own pre-registration.
- Not to be used for: establishing legal equivalence (textual similarity only, no lawyer validated the proxy),
  contracts outside English US-style drafting, and clauses longer than the encoder's window are read truncated.

## How to reproduce

```bash
make setup      # .venv with the pinned course environment, package installed in editable mode
make test       # unit tests
make smoke      # the whole pipeline on a per-class subset (FAST_RUN=1), then every notebook
```

GPU runs (m4) on Colab: open [`colab/run_m4.ipynb`](https://colab.research.google.com/github/jbouniol/nlp-project/blob/main/colab/run_m4.ipynb),
the run cards of every DistilBERT and LoRA run, in order.
The 10-epoch follow-up has its own runner,
[`colab/run_m4_10epochs.ipynb`](https://colab.research.google.com/github/jbouniol/nlp-project/blob/main/colab/run_m4_10epochs.ipynb). From the command line:

```bash
python scripts/train.py --model tfidf                                  # m1 (= make m1)
python scripts/search_lstm.py                                          # m3: one factor at a time, on validation
python scripts/train.py --model lora --search --lr-lora 1e-3 --seed 0  # m4: a validation-only run
python scripts/predict_test.py --name lora_lr1e-3_seed0                # the chosen run predicts the test split, once
python scripts/retrieval.py --encoder minilm --classifier-run lora_lr1e-3_ep10_seed0  # m2: one encoder on validation (= make m2 for all)
python scripts/retrieval.py --choose && python scripts/retrieval.py --final  # the rule, then the test split, once
```
